# DeepSeek 大模型 Agent 岗位面试题总结与参考答案

> 素材来源:一位"前阿里技术专家"面完 DeepSeek 后的复盘视频文案。
> 面试共三轮:一面深挖项目细节(70 分钟)、二面工程架构设计(从 0 到 1)、三面认知判断(定级面)。
> 本文把每一轮的问题逐条拆出,并给出**带工程落地视角**的参考答案。八股式空泛回答在这类面试里是减分项,答案尽量往"真实做过、踩过坑、有数据"的方向组织。

## 面试整体特征(先看这个)

| 轮次 | 面试官 | 时长 | 核心考察 | 一句话本质 |
|------|--------|------|----------|-----------|

| 二面 | 技术总监 | 晚上加面 | 系统架构 + 工程思维 | **落地**:能不能把系统做稳、做可控、上线不出事 |

3. **连环追问到底**——答含糊会被连续追问"改了哪块逻辑""效果提升百分之多少",套方案没真做过撑不过 20 分钟。

# 一面:项目细节深挖(会话记忆 / 长期记忆 / 成本 / 选型 / 故障)

## 一、会话记忆(短期记忆)

### Q1. 会话记忆用 MessageWindow 还是 TokenWindow?线上为什么这么选?

**先讲两者区别:**
- **MessageWindow(按消息条数)**:保留最近 N 轮对话。实现简单,但每条消息长度不定——遇到长消息会把上下文顶爆,遇到短消息又浪费窗口。
- **TokenWindow(按 Token 总量)**:保留最近累计不超过 M 个 Token 的消息。能精确控制上下文长度和成本,和 LLM 的真实硬约束(Token)对齐。

**线上选择与理由:**
- 主选 **TokenWindow**,因为模型的硬约束是 Token 而不是消息条数,按 Token 控制才能同时兜住"上下文不溢出"和"成本可预测"两件事。
- 实际落地常用**混合策略**:
  - System Prompt / 关键指令 **pin 住**不参与滑动;
  - 近期对话保留**完整原文**;
  - 更早的历史做**滚动摘要(summary buffer)**,把 N 轮前的对话压成一段摘要,既省 Token 又不丢关键信息;
  - 单条超长消息(如用户贴一大段文本)先单独摘要,防止一条消息就把窗口占满。

> 加分点:能说出"为什么不是纯 MessageWindow"——因为线上消息长度方差极大,纯条数窗口无法保证成本和上下文的确定性。

### Q2. Redis 持久化时会话过期策略怎么定?

- **滑动过期 TTL**:给会话 key 设 TTL(如 30 分钟 ~ 24 小时),每次交互 `EXPIRE` 刷新,用户活跃就一直续命,静默后自动回收。
- **冷热分层**:活跃会话放 Redis,长时间不活跃的会话在过期前**落库**(MySQL / 对象存储)归档,需要时再回捞,避免 Redis 内存无限膨胀。
- **过期前触发摘要**:会话即将过期/归档时,把有价值的信息**沉淀进长期记忆**(向量库),而不是直接丢弃。
- **内存兜底**:配置 `maxmemory` + LRU/LFU 淘汰策略作为最后防线。
- **Key 设计**:`session:{userId}:{sessionId}`,便于按用户批量管理和排查。

### Q3. 有没有遇到过并发会话冲突问题?怎么解决?

**典型场景**:同一会话多端(手机 + 网页)同时发消息,或前一轮还没返回用户又发了一条,导致消息乱序、上下文覆盖、摘要写花。

**解决方案:**
- **单会话串行化**:用 Redis 分布式锁(`SET NX` / Redlock)对同一 `sessionId` 的写操作串行化;或走消息队列按会话分区顺序消费。
- **Append-only 存储**:用 Redis List / Stream 追加消息,不做覆盖写,天然避免"后写覆盖先写"。
- **乐观锁 / 版本号**:摘要、状态这类需要更新的字段带 version,CAS 更新,冲突则重试。
- **幂等**:每条消息带唯一 `messageId`,消费端去重,防止重复提交。

## 二、长期记忆

### Q4. 长期记忆用向量库存储对吗?记忆越来越多、检索越来越不精准怎么优化?

**是的,长期记忆主流是向量库 + 语义检索。膨胀导致检索退化是必然会遇到的问题,原因是:噪声记忆变多、相似记忆互相挤占召回名额、旧记忆过时仍被召回。**

**线上优化手段(分层递进):**

1. **记忆分层**:区分**情节记忆**(具体对话事件)、**语义记忆**(提炼出的稳定事实/偏好)、**摘要记忆**。检索时优先命中高价值的语义记忆。
2. **写入侧治理**:
   - 写入前做**去重/合并**——新记忆与已有记忆相似度超阈值就合并更新,而不是无脑新增;
   - 给记忆打**重要性分数**,低价值的少存或不存。
3. **检索侧优化**:
   - **混合检索**:向量召回 + BM25/关键词召回,取长补短;
   - **Rerank 重排**:用 cross-encoder 对召回结果精排,大幅提升 Top-K 精度;
   - **元数据过滤**:按用户、时间、类型先过滤再检索,缩小候选;
   - **时间衰减**:给记忆加时间权重,旧记忆自然降权。
4. **遗忘机制**:定期做**记忆压缩/遗忘**(LRU + 重要性驱动),把一堆碎片记忆归纳成摘要,类似人脑遗忘曲线。
5. **基础工程**:优化 embedding 模型、合理 chunk 大小、Query 改写 / HyDE 提升召回质量。

> 追问会问到"线上具体怎么优化的、效果提升多少",要能说出改了哪一步(如加了 rerank)、指标从多少提到多少(如检索准确率 68%→85%)。

### Q5. 上下文 Token 溢出的兜底方案是什么?

**分级兜底,从"优雅"到"硬截断":**
1. **优先级保留**:System Prompt + 最新用户 query 永远保留,这是底线。
2. **历史压缩**:超阈值时先把旧对话滚动摘要,而不是直接删。
3. **工具结果裁剪**:工具/检索返回的大段结果先摘要或截断再进上下文(往往是溢出主因)。
4. **长文档处理**:用 Map-Reduce / Refine 分块处理,不硬塞。
5. **主动预估**:调用前预估 Token,超阈值提前触发压缩,而不是等报错。
6. **模型降级路由**:切换到更大上下文窗口的模型作为 fallback。
7. **硬兜底**:实在超了就截断最老内容 + 给用户明确提示,绝不让请求直接 500。

## 三、成本

### Q6. 单用户日均 Token 成本多少?百万级流量下怎么控制?

**度量口径**:单用户日均 Token = Σ(输入 Token + 输出 Token) × 对应单价;要按输入/输出分开算(输出通常更贵)。

**百万级流量控制手段:**
- **模型路由(最有效)**:简单意图/闲聊用小模型或便宜模型,复杂推理才上大模型,可省 50%+ 成本。
- **Prompt 缓存 / 语义缓存**:相同或语义相近的 query 直接命中缓存返回,不走模型;固定前缀走 Prompt Caching。
- **上下文瘦身**:摘要、裁剪、精简 few-shot,直接砍输入 Token。
- **输出约束**:设 `max_tokens`、鼓励简洁输出、流式下满足条件提前停止。
- **限流与配额**:每用户每日 Token/请求上限,防止个别用户拖垮成本。
- **可观测**:按用户/场景/模型埋点 Token 用量,做报表 + 预算告警 + 成本熔断。

### Q7. 有没有做过调用拦截?用户恶意刷长文本怎么限制?

**做过,而且要在网关层就拦,不能等打到模型才拦(那样钱已经花了)。**
- **输入长度上限**:单请求输入 Token/字符硬上限,超限直接拒绝。
- **频率限流**:令牌桶/漏桶,按 user / IP / API Key 多维限流。
- **配额熔断**:每用户每日 Token 配额,超额降级(转小模型)或拒绝。
- **内容检测**:检测异常超长文本、高度重复内容、疑似脚本刷量的模式。
- **鉴权 + 风控**:接口鉴权、异常行为打分、黑名单。
- **成本熔断**:整体或单用户成本超预算自动降级/限流,保护大盘。

## 四、模型选型

### Q8. 这个场景为什么用基座模型不用微调模型?

**以企业知识库 / Agent 场景为例:**
- **知识频繁更新**:企业知识天天变,微调把知识"焊死"进权重,更新就得重训,成本高还会灾难性遗忘。→ 用 **RAG + 基座** 更新知识只需更新向量库,灵活得多。
- **基座通用能力强**:指令遵循、推理、工具调用能力更全面,Agent 需要的正是这些通用能力。
- **微调的适用场景**:固定风格/格式输出、特定专有任务、且有足够高质量标注数据时,微调(或 LoRA)才划算。
- **工程结论**:**RAG 解决"知识注入",微调解决"行为/格式对齐"**,两者不是二选一。多数场景先用 RAG + Prompt 工程快速上线,数据积累够了再评估是否上 LoRA 微调。

### Q9. 选型时拿什么数据做判断?

- **业务评测集(核心)**:用真实业务 query 构建 eval set,而不是拿公开榜单拍脑袋。
- **多维指标**:任务准确率/召回、**幻觉率**、指令遵循、格式合规、延迟(P95)、成本、上下文长度、并发能力。
- **评估方法**:离线 benchmark + 线上 A/B;人工标注 + LLM-as-a-Judge 结合。
- **约束条件**:数据合规(能否出境)、是否需要私有化部署、License。
- 最终是 **性能 / 成本 / 合规 / 延迟** 的综合权衡,给出可量化的对比表。

### Q10. 线上故障排查(面试官连续追问三次的那个点)

这不是一道题,而是一种**追问模式**:答含糊必被追到底。正确的讲法结构:
> **现象 → 定位 → 根因 → 改动 → 验证 → 量化效果**

- **现象**:什么指标异常(如超时率飙升 / 答非所问)。
- **定位**:靠什么发现的——全链路 Trace(每次 LLM 调用、工具调用、Token、延迟)、日志、监控告警。
- **根因**:具体是哪一步、哪块逻辑出问题。
- **改动**:**具体改了哪块逻辑**(这是面试官追问的关键)。
- **效果**:改完指标从多少变到多少,**说得出百分比**。

> 结论:一面本质是**打假**。只用 LangChain 拼个 Demo、没有线上可观测体系、说不出改动细节和量化效果,这一轮必挂。

# 二面:从 0 到 1 设计商用 Agent 系统(工程思维)

> 形式:共享屏幕**边画架构图边被追问**,全是线上落地问题,不考怎么调框架。

### Q11 / Q12. 系统模块怎么拆分?各模块职责?模块间用什么通信?为什么这么拆?

**分层架构(从上到下):**

| 层 | 职责 | 关键点 |
|----|------|--------|
| **接入层 / 网关** | 鉴权、限流、路由、协议转换 | 成本与安全的第一道闸 |
| **会话编排层 (Orchestrator)** | 对话管理、记忆读写、规划调度入口 | 系统大脑的调度中枢 |
| **Agent 核心** | Planner(规划)、Executor(执行)、Reflection(反思/自检) | ReAct / Plan-Execute 在这里 |
| **工具层** | 工具注册中心、工具调用、代码沙箱 | 工具可插拔、有 schema |
| **记忆层** | 短期(Redis)、长期(向量库)、结构化(DB) | 冷热分层 |
| **模型层** | 多模型接入、路由、Fallback、限流 | 可单独扩容 |
| **可观测 & 风控** | 全链路 Trace、监控、审计、权限 | 上线不出事的保障 |

**模块间通信:**
- **同步**、低延迟调用用 RPC/gRPC 或 HTTP;
- **异步**、耗时任务(长任务、批处理)用消息队列(Kafka/RabbitMQ)解耦,防止阻塞;
- **工具调用**走统一协议(Function Calling / MCP),工具即插即用。

**为什么这么拆(拆分原则):**
- **高内聚低耦合**:每层职责单一,改一层不牵连全局。
- **独立伸缩**:模型层是资源大头,单独扩容;工具层按需扩。
- **故障隔离**:某个工具挂了不拖垮整个系统。
- **可替换/可插拔**:模型、工具、记忆后端都能替换,不被单一供应商绑定。

### Q13. 怎么判断"单工具简单任务"还是"多步拆解复杂任务"?拆解粒度怎么控制?

- **判定**:前置一个 **Router / Planner**,用 LLM 分类或规则判断意图复杂度。
  - **简单任务**:意图明确、单步/单工具可完成 → 直接调用,不进规划,省延迟省钱。
  - **复杂任务**:需多步、多工具、有依赖 → 进入 Planning,拆成子任务 DAG。
- **拆解粒度原则**:每个子任务要 **可执行、可验证、单一职责**。
  - 太细 → 步数爆炸、编排 overhead 大、易失控;
  - 太粗 → 单步不可控、失败难定位。
  - 设**最大步数上限**防止无限循环;子任务要有明确的成功/失败判定。
- 方法论:ReAct(边想边做)、Plan-and-Execute(先规划后执行)、必要时树搜索。

### Q14. 任务执行到一半某步失败了,怎么判断重试 / 回滚 / 重新规划?触发条件分别是什么?

**核心是先给错误分类,再决定策略:**

| 策略 | 触发条件 | 说明 |
|------|----------|------|
| **重试 (Retry)** | 瞬时/可恢复错误:网络超时、限流 429、5xx、模型偶发抽风 | 指数退避 + 最大次数;要求操作幂等 |
| **回滚 (Rollback)** | 有**副作用**的操作失败:写库、下单、发消息 | Saga 补偿事务,回滚已执行的步骤,保证一致性 |
| **重新规划 (Replan)** | 重试仍失败 / 结果不符合预期 / 环境已变化 / 前提假设被推翻 | 带着失败信息回到 Planner 重新规划路径 |

**工程配套:**
- **错误分类**:可恢复 vs 不可恢复、有无副作用、是否幂等——这是决策的前提。
- **Checkpoint**:关键步骤存快照,失败可从断点恢复,不用从头再来。
- **人工兜底 / 降级**:多次失败后转人工(Human-in-the-loop)或给降级结果,绝不静默死循环。

### Q15. 多工具联动(联网检索 / 关键词检索 / 代码解析)怎么配合?

- **统一工具接口 + 编排层**:每个工具有清晰的 schema 描述,让 LLM 能正确选择和填参。
- **数据流转**:上一步输出作为下一步输入(变量传递 / 黑板 Blackboard 模式共享中间结果)。
- **并行 vs 串行**:无依赖的工具并发调用降延迟(如同时联网检索 + 关键词检索),有依赖的串行。
- **结果聚合**:多路结果去重、融合、rerank 后再交给模型。
- **缓存**:工具结果缓存,相同调用不重复花钱/耗时。

### Q16. 工具调用权限怎么管控?怎么防止用户通过 Agent 越权操作?

**这是二面容易答不细的点(视频作者也栽在这里),要答出层次:**
- **最小权限原则**:每个工具、每个用户绑定权限 scope,默认拒绝。
- **身份透传**:用户身份贯穿整个工具调用链,工具用**用户的权限**而不是 Agent 的超级权限执行——这是防越权的关键,否则 Agent 成了权限黑洞。
- **高危操作二次确认**:删除、支付、外发等走 Human-in-the-loop 审批。
- **沙箱隔离**:代码执行、文件操作放沙箱,限制网络/文件系统。
- **审计日志**:所有工具调用可追溯(谁、何时、调了什么、参数、结果)。
- **防 Prompt 注入**:输入检测 + 工具白名单 + 输出校验,防止用户用话术诱导 Agent 越权。

> 二面本质:DeepSeek 不关心你用什么框架,要的是"**做稳定、做可控、上线不出事**"。

# 三面:认知与行业判断(定级面 / 决定薪资)

> 不问代码、不聊技术,全是认知和判断。本质是看你**配不配高薪、能不能独当一面**。

### Q17. 你怎么认准 Agent 这个赛道的?是长期风口还是短期热点?长期落地方向有哪些?

**判断:长期风口,短期有泡沫,长期确定性高。**
- **底层逻辑**:LLM 能力还在持续爬坡,而 Agent 是把模型能力**转化为实际生产力**的载体——从"能聊"(Copilot 辅助)走向"能干活"(Autopilot 自动执行)是必然趋势。
- **短期**:概念热、Demo 多、真正稳定上线的少,存在泡沫;但泡沫破的是"套壳 Demo",留下的是"真解决问题的落地系统"。
- **长期落地方向**:
  - 垂直领域自动化:客服、编程(Coding Agent)、数据分析、办公/流程自动化(替代 RPA);
  - 企业侧:知识管理、内部流程编排、垂直行业 Agent(法律/医疗/金融)。
  - **ToB 效率工具会先跑通**(下文详述)。

### Q18. 做了这么多 Agent 项目,和市面上普通大模型开发者比,核心竞争力在哪?

- **不是"会调框架"**——LangChain 谁都会拼。
- **是端到端把 Agent 做上线、做稳定的工程能力**:踩过线上坑,有可观测 / 成本 / 风控 / 容错的实战经验。
- **是对业务和场景的判断力**:知道什么该用 RAG、什么该微调、什么场景根本不该上 Agent。
- 一句话:**"我做过能扛百万流量、上线不出事的系统",而不是"我跑通过一个 Demo"。**

### Q19. 1-2 年内 Agent 最大瓶颈在哪?模型能力还是工程能力?ToB 还是 ToC 先跑通?

**瓶颈:短期内工程能力是更大的瓶颈。**
- 模型能力在快速进步(上下文、推理、工具调用都在涨);
- 但**可靠性、成本、幻觉控制、长任务稳定性、效果评估**这些工程问题才是"上线不出事"的拦路虎,当前更卡脖子。

**ToB 先跑通:**
- ToB 有**明确付费意愿**、场景**可闭环**、且**容错空间大**(出错有人工兜底、有审批流);
- ToC 要求更高的可靠性 + 更低的成本 + 更强的通用性,门槛更高,会更晚成熟。

### Q20. 如果让你从 0 到 1 带一条 Agent 业务线,从招人到落地商业化,第一步做什么?

**第一步不是急着招人堆技术,而是选对场景、验证 PMF。**
1. **选场景(最关键)**:找**高价值、可闭环、容错、有数据**的垂直场景,定义清晰的北极星指标——选错场景后面全白干。
2. **做 MVP 验 PMF**:小步快跑做最小可用版本,验证是否真解决问题、用户是否真买单。
3. **再招人**:先招**能落地的全栈工程 + 懂业务的人**,而不是一上来堆算法。
4. **做数据飞轮**:用真实使用数据持续迭代,形成"用得越多→越好用→用得更多"的正循环。

> 三面要的不是埋头写代码的工具人,而是**对赛道有思考、能扛事、能独当一面**的人。
